# Hardware recheck — 10 November 2026

## Wiring and simultaneous input
Keep both UNO R3 A4 pins on Main SDA/A4, both A5 pins on Main SCL/A5, and all three grounds connected. The LCD shares that same header bus. The R4 is the sole I2C controller; each R3 replies only when addressed. Both R3s sample their controls independently. Separate SDA/SCL ports are not needed.

Diagnostic addresses: empty/Architect COM6 = 0x10, Explorer COM8 = 0x11, LCD = 0x27. Production role addresses differ: do not mix production and diagnostic firmware.

- All three USB boards detected using their previously recorded USB serial identifiers.
- LCD detected at 0x27; initialization succeeded and both test strings read back with zero errors. User confirmed the display is readable.
- Explorer X and Y each reached 0–1023. D2 registered seven pressed samples and a latched count of three presses during nov10-wifi-bus.txt.
- R4 access point started at 192.168.4.1. Laptop saw its SSID, joined it, and received five successful HTTP responses containing both R3 readings. Previous laptop Wi-Fi connection was restored.
- The HTTP test is diagnostic data transfer, not a complete game integration test.

- Architect servo test completed and detached. User clarified that the horn moved a small amount left/right, matching the intentionally small test. This verifies basic motion, not full gate travel or loaded operation.
- Final undisturbed 100 kHz capture: 690/690 successful exchanges over 35 seconds (345 per R3). This does not erase the earlier intermittent failures.

## Intermittent bus failures — not resolved
The first 100 kHz capture contained 16 unsuccessful command/read exchanges out of 1,162; the next contained four out of 970. Several failures returned no bytes; some commands were not acknowledged. Successful packets passed checksum and command-echo checks.
A 50 kHz comparison had 142 failures out of 904. The user was adding a servo around this period, so this is not a controlled comparison and cannot establish a cause. Return to 100 kHz. Inspect connection seating, ground, existing pull-ups and power with power disconnected before changing hardware. No evidence establishes address collisions as the cause.

## Output-test details and current firmware
The diagnostic Main supports serial command T: red D3, green D5, blue D9, then a short D6 tone, finally outputs off. It assumes individually resisted common-cathode RGB wiring. Outputs are not tested by default at boot.
Architect servo test source supports V on its own USB serial port: D9 pulses 1500, 1400, 1600, 1500 microseconds, then detach. This is a small unloaded test, not a gate travel calibration. This source was uploaded to COM6 and run once. User reports signal D9, power from R3 5V, common ground, and only an X-shaped horn fitted. Use a separate regulated 5V supply with common ground for the finished gate. Do not treat this brief unloaded test as proof that the Arduino supply can support a loaded servo.

All boards remain on diagnostic firmware. Main is back at 100 kHz. Main RGB/buzzer outputs are off and Architect servo is detached in software. No motor test runs automatically at boot.

The servo capture includes an intentional COM6 reset when its USB serial port opened, producing 16 unsuccessful/initializing polls before the command. Both R3s communicated successfully after this reset; this expected reset is not evidence of a servo-induced brownout. The log confirms SERVO_TEST_END detached.
